Add real-time multiplayer support via a two-layer API/adapter architecture.

**`jspsych`** — new top-level `jsPsych.multiplayer` module exposing shared data in which each participant writes their own data and everyone can read everyone's:

- Sessions: `connect(adapter, options)` opens a session (cancellable with an `AbortSignal`, and given up after `connectTimeout`, 20 s by default) and `jsPsych.multiplayer` forwards every method to it. `disconnect()` closes it, or cancels a pending connect once the adapter has cleaned up. Reads keep returning the last state after the session closes.
- Writing: `update(data)` shallow-merges into this participant's data (a key set to `undefined` is removed) and `replace(data)` replaces it. Reads reflect a write at once; the session sends one write at a time and combines writes made in the meantime. A failed write is retried with backoff until it succeeds or the connection closes. Data must be plain JSON.
- Scopes: during a trial, reads and writes use that trial's own part of the shared data, so data from one trial never shows up in another. The scope defaults to the trial's position in the timeline, which is the same for every participant running the same timeline; the new `multiplayer_scope` trial parameter names it instead. `{ scope: "session" }` uses data that lasts the whole session, which is also the default outside trials. Later trials read an earlier trial's results from jsPsych's data.
- Reading: `getAll()`, `get(participantId)`, `subscribe(callback)`, and `wait(condition, { timeout, signal, participants })` share one frozen snapshot per change. Subscriptions and waits made during a trial end with the trial, unless they use the session scope. Timeouts must be a positive number of milliseconds or `null` for none; anything else throws.
- Presence: `presence()` reports each participant as `connected`, `away`, or `left` (after a configurable `dropoutTimeout`). `left` is final, and the group agrees on it: a participant who sees someone leave tells the group, and others who have also lost sight of them agree. A participant who reloads counts as having left, and sees `restarted` on their own side. `onParticipantLeft` and `onStatusChange` report dropouts and connection changes; `reconnectTimeout` gives up on a connection that stays down.
- Groups: for backends that put arriving participants into groups, `group()` reports the group's `size`, `members`, and whether it is `sealed` (nobody new can join; the roster is final), and only members' data is shown. `waitForGroup({ timeout, signal })` resolves once the group is sealed, for a waiting room, and `sealGroup()` seals it early.
- Shared randomness: `random(key)`, `randomInt(key, lower, upper)`, `shuffle(key, array)`, and `sample(key, array, size)` return the same values for every participant without sending anything. Each value is a pure function of the session's seed, the method, and the key, so call order, extra calls, and reloads don't matter. The seed is the adapter's session ID, or the `randomSeed` connect option.
- Data: by default every row of jsPsych's data gets `multiplayer_participant_id` and `multiplayer_session_id`, so a group's data can be joined; `recordIds: false` turns this off.
- Errors: the API's own errors are `MultiplayerError`s whose `code` is `timeout`, `cancelled`, `participant_left`, `connection_lost`, `not_connected`, or `unsupported`.

Backend adapters (e.g. JATOS, Firebase) and multiplayer plugins are distributed as separate packages in the [jspsych-multiplayer](https://github.com/jspsych/jspsych-multiplayer) ecosystem repository; this change adds only the core API and the `MultiplayerAdapter` / `MultiplayerConnection` interfaces they implement. A connection reports a `participantId` and a `sessionId` that is the same for every participant in the group, and can report the group's membership with the optional `group()` and `sealGroup()` methods; an adapter that forms groups must report a seal to every member.
